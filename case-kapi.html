The eval that killed my roadmap

I spent weeks improving retrieval. Then I measured, and retrieval was mostly fine.

Problem

A demo that works is not a product that works

Kapi is an AI product analytics agent I built end to end. You ask a product question in plain language, it retrieves what it needs, and it answers. Built with retrieval, embeddings, and LLM APIs, on top of the open-source OpenClaw framework by Peter Steinberger, MIT licensed.

It demoed well, which is exactly the problem. Every AI product demos well, because you drive the demo. What I could not answer was the only question that matters before anyone relies on it. How often is it wrong, and what kind of wrong?

My working assumption was that retrieval was the weak link. That is where I was spending my time. It is also the intuitive answer, because when a grounded system says something false, the obvious story is that it fetched the wrong context.

Action

Build the measurement before trusting the intuition

1 · A labeled eval set, not a vibe check

I built a 51-case labeled evaluation suite run against the live system, real model and real retrieval. Each case was scored on separate axes rather than one blended quality number, because "good" here is at least two different things.

  • Competence, whether the answer is correct and useful
  • Honesty, whether it refuses when it should refuse

Those have to be separate. A system that answers everything confidently scores well on one and catastrophically on the other, and a single blended score would hide it.

Judge agreement, Cohen's κ = 0.556. Moderate, which I report rather than hide, because it bounds how much any single score is worth.

2 · Classify the failures instead of counting them

A score tells you there is a problem. It does not tell you which problem. So I categorized every failure by what actually went wrong.

The top two are both the same underlying behavior. The system talks when it should stop.

3 · Attribute fault to a component

Failure mode still is not enough to act on, because a hallucinated fact could be caused by bad context or by the model ignoring good context. So the last step was attributing each failure to the component responsible.

Result

Two completely different roadmaps

The eval did not confirm my plan. It replaced it.

Retrieval was mostly fine. The real product problem was the agent answering confidently when it should have refused. If I had trusted my intuition for another month, I would have shipped a better retriever attached to the same failure.

  • Roadmap redirected from retrieval quality toward answer reliability and appropriate refusal
  • Competence and honesty tracked separately from then on, so improving one at the cost of the other is visible instead of invisible
  • Judge agreement reported alongside every score, because a score from an unreliable judge is not a score

The transferable lesson is smaller than the numbers make it sound. An eval is not a QA step at the end. It is the thing that tells you which roadmap you are actually on. I wrote mine because I wanted a number for a deck, and it cost me a plan I liked.

What this evidence does not support

Fifty-one cases is small, and κ = 0.556 is moderate agreement rather than strong. These numbers are good enough to redirect my own effort, which is what I used them for. They are not good enough to publish as a benchmark or to compare systems against each other. I also want to be precise that this is the live evaluation. I ran a separate offline evaluation of the deterministic routing layer on a 31-case dev set, and those two sets of numbers are not interchangeable.
