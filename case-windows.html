What does "works on Windows" actually mean?

The request had no definition inside it. Three groups of people each had a different one, and nobody had picked.

Problem

Feature parity is not a requirement

Digital Robotics is a twelve-person startup building agent-driven analysis products for regulated industries. The product was Mac-first. The request that reached me was, in effect, bring it to Windows with feature parity.

That sounds like an engineering task. It is not, because "feature parity" is not a definition of done, it is a placeholder for one. Depending on who you asked, done meant three different things.

The same word, three meanings
Engineering · "the application and its services run on Windows"
reasonable
End user · "I can install it and use it without help"
reasonable
Internal demo · "we can launch it again tomorrow without an engineer"
reasonable
All three are defensible. Shipping against the first one produces something that technically works and that no customer can use.

The cost of guessing wrong here is specific. If we shipped against the engineering definition, every Windows demo becomes a development environment, every customer session needs a person who knows which process crashed, and the product looks broken to exactly the people we were trying to reach.

Action

Pick the users, then write down what has to be true

1 · Name the two groups the MVP is for

I did not run a six-week persona study. In an early-stage startup you rarely get to. What I did was notice that "Windows version works" meant different things to different people and force a choice between them, defining the MVP around the two groups whose experience actually decided whether this shipped.

  • The non-technical Windows user. Their test is one sentence. Can I install it, open it, and use it without understanding the stack underneath? No Python or Node environment, no terminal commands, no manually starting services, no knowing which background process died.
  • The internal demo and validation team. Leadership and colleagues who need to launch the Windows build repeatedly. Their test is different. Can we launch the same environment again, reliably, without an engineer in the room?

2 · Reframe the definition of done

I moved the definition of done from "the software runs on Windows" to "a target user can install, launch, recover, and relaunch it without developer intervention."

That one sentence is the entire product contribution. Everything after it is execution against a target that now exists.

3 · Turn it into acceptance criteria someone else can check

A definition nobody can verify is an opinion. I broke it into four categories, each one checkable by a person who was not me.

Acceptance criteria · four categories
Setup
  • One-click installation
  • No manual environment configuration
  • No terminal dependency for normal use
Launch
  • Required services start automatically
  • Consistent application startup
  • Warm launch around 7 seconds
Reliability
  • Duplicate processes prevented
  • Failed services detected
  • Automatic recovery where possible
Lifecycle
  • Predictable shutdown
  • Clean relaunch
  • User never manages background services
Warm launch measured from launcher invocation to app-ready on our test setup.

4 · Then do the same thing one level up

The same ambiguity existed in what we should be showing customers at all. There were more than six candidate use cases being discussed for pre-launch positioning and demos, and the team was trying to be ready for all of them. I structured that comparison rather than deciding it, scoring each candidate on three dimensions and working through the tradeoffs with leadership.

Relevance asked whether it maps to a problem the customer already has. Readiness asked whether the product could support it without an engineer intervening mid-demo, assessed with the technical team. Dependency risk asked how many other things had to be finished first, which is what separates a good long-term idea from a good idea for this stage.
Result

The outcome was not seven seconds

It is tempting to lead with the performance number. That would be the wrong summary.

The real outcome was reducing operational dependency on engineering. Instead of treating every Windows demo or validation session like a development environment, we had a repeatable product experience that could be installed, launched, and recovered consistently.

  • Windows moved from a developer-dependent setup to one-click installation
  • Automatic recovery when a background service fails, so a crash stops being a support event
  • Warm launch around 7 seconds, which made relaunching cheap enough that demos stopped being precious
  • Leadership discussion moved from "AI can do many things" to "here are the three we are showing"

What I took from it is that technical parity was never the goal, and the hardest part was not code. It was that the problem arrived undefined, nobody else was going to define it, and the cost of guessing was a product that passed engineering and failed a customer.

Being precise about my role

The seven seconds is an observed result, not a target I optimized toward or a company KPI. We used warm-launch time as a practical validation check because repeatability mattered for demos, and that is what it came out at. On the use-case work, I want to be careful not to overstate it. I was not independently setting company strategy. My contribution was structuring the comparison, clarifying the customer problem behind each candidate, surfacing the tradeoffs, and helping leadership make the call.
